## A decisão

Este site vai ser bilíngue, mas hoje só tem português. Eu podia escrever tudo em português e pensar no inglês depois.
O problema é que "depois" quer dizer mudar URLs que já foram compartilhadas e reescrever páginas que assumem um idioma.

Então decidi o formato das URLs antes do primeiro artigo:

- Português é o idioma padrão e não tem prefixo: `/blog/por-que-escolhi-astro`.
- Inglês fica em `/en`, com o slug traduzido. Quando este artigo tiver versão em inglês, vai ser algo como
  `/en/blog/why-i-chose-astro`.
- Os segmentos de rota são sempre em inglês (`blog`, `projects`, `about`). Só o slug é traduzido.

## Uma lista de idiomas, um lugar

Os idiomas ficam em um arquivo só. O `astro.config.mjs` importa dele, os schemas também, e os componentes recebem o
tipo `Locale` em vez de uma string qualquer.

```ts title="src/i18n/config.ts"
export const LOCALES = ['pt', 'en'] as const;
export type Locale = (typeof LOCALES)[number];

export const DEFAULT_LOCALE: Locale = 'pt';

/** Locales that already have published content. The language switcher stays hidden until this has more than one entry. */
export const ENABLED_LOCALES: readonly Locale[] = ['pt'];
```

O inglês já está em `LOCALES`, então o roteamento do Astro já conhece `/en`. O que ainda não existe é conteúdo, e é
por isso que `ENABLED_LOCALES` tem só `pt`. Enquanto for assim, o seletor de idioma não aparece. Ninguém clica num
botão que leva a uma página vazia.

```js title="astro.config.mjs"
i18n: {
  defaultLocale: DEFAULT_LOCALE,
  locales: [...LOCALES],
  routing: {
    prefixDefaultLocale: false,
  },
},
```

Não uso biblioteca de i18n. O roteamento é o nativo do Astro, e os textos da interface ficam num dicionário tipado em
`src/i18n/ui.ts`. O inglês é declarado como `Record<UiKey, string>`, então se faltar uma chave o `pnpm check` falha.

## O slug mora no frontmatter

O nome do arquivo não decide a URL. Cada artigo declara o próprio slug, e o schema garante o formato.

```ts title="src/content.config.ts"
const localized = {
  lang: z.enum(LOCALES),
  /** Shared key that links translations of the same item across locales. */
  translationKey: z.string().min(1),
  /** Translated URL slug, e.g. `construindo-o-prumo` / `building-prumo`. */
  slug: z.string().regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/, 'Slug must be kebab-case ASCII'),
};
```

A regex barra acento e maiúscula. `construíndo-o-prumo` não passa no build, então não vira uma URL com `%C3%AD` no
meio.

Os arquivos ficam separados por pasta de idioma, `posts/pt/` e `posts/en/`. Aqui tem uma pegadinha: quando o
frontmatter tem `slug`, o loader `glob` usa esse campo como id da entrada. Um projeto chamado Prumo teria o slug
`prumo` nos dois idiomas, e as duas entradas colidiriam. Por isso o id é o caminho do arquivo:

```ts title="src/content.config.ts"
/** Entry id = path without extension (e.g. `pt/prumo`), so equal slugs in different locales never collide. */
const generateId = ({ entry }: { entry: string }) => entry.replace(/\.(mdx?|json)$/, '');
```

## Uma chave liga as traduções

Com slugs diferentes, `por-que-escolhi-astro` e `why-i-chose-astro` não têm nada em comum que o código consiga ver.
O `translationKey` resolve isso. É uma chave em inglês, estável, repetida nas duas versões.

```ts title="src/lib/content.ts"
export function findTranslation<T extends { data: { lang: Locale; translationKey: string } }>(
  entries: readonly T[],
  entry: T,
  lang: Locale,
): T | undefined {
  return entries.find((e) => e.data.lang === lang && e.data.translationKey === entry.data.translationKey);
}
```

A página do artigo usa essa função para montar os `alternates`. O componente `SEO` transforma cada um em
`<link rel="alternate" hreflang>`, e o seletor de idioma no cabeçalho usa a mesma lista. Quando um artigo ainda não tem tradução,
a lista fica vazia e nada é anunciado.

## URLs montadas num lugar só

Nenhum componente escreve `/en/` na mão. Todo link interno passa por uma função que chama o `getRelativeLocaleUrl`
do Astro:

```ts title="src/i18n/utils.ts"
export function localizePath(path: string, lang: Locale): string {
  return getRelativeLocaleUrl(lang, path);
}
```

Ela é curta de propósito. O `getRelativeLocaleUrl` lê a configuração de i18n, o `trailingSlash: 'never'` e o
`build.format: 'file'`, então o link gerado é o mesmo que o build publica. Se eu mudar uma dessas opções, os links
mudam junto.

## O que ficou para depois

As rotas em inglês ainda não existem. Quando o primeiro artigo em inglês entrar, faltam três passos:

1. Adicionar `'en'` em `ENABLED_LOCALES`, o que mostra o seletor de idioma.
2. Criar `src/pages/en/` espelhando as páginas atuais.
3. Incluir as entradas em inglês no `getStaticPaths` do artigo, que hoje lê só o idioma padrão.
